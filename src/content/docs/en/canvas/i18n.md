**EpoCanvas Docs** ships complete content-level multilingual support: the UI text (navigation bar, sidebar, search hints, and so on) and the body text of every document are each available in 10 independent languages. After selecting a language from the top-right corner of the page, the reader is taken to the same article in that language, with the body text and the UI switching together.

---

## Supported Languages

The site currently offers 10 languages, with Simplified Chinese as the default:

| Language | Language name | URL prefix | UI abbreviation |
| :--- | :--- | :--- | :--- |
| 简体中文 | **Simplified Chinese** (default) | none | ZH |
| 繁體中文 | Traditional Chinese | `/zh-tw/` | TW |
| English | English | `/en/` | EN |
| 日本語 | Japanese | `/ja/` | JA |
| 한국어 | Korean | `/ko/` | KO |
| Español | Spanish | `/es/` | ES |
| Français | French | `/fr/` | FR |
| Deutsch | German | `/de/` | DE |
| Русский | Russian | `/ru/` | RU |
| Português | Portuguese | `/pt/` | PT |

The language list lives in `SUPPORTED_LANGUAGES` in `src/utils/i18n.ts`. In `astro.config.mjs`, `locales` registers routes and `LOCALE_DIRS` identifies non-default language directories. Adding a language also requires updating translation dictionaries and check scripts, not just `locales`.

## How to Switch Languages

1. Find the language button on the right side of the top navigation bar (it shows the abbreviation of the current language, such as `ZH`);
2. Click the button and a dropdown menu lists all 10 languages;
3. Click the target language (for example `English` or `日本語`);
4. The browser navigates to the current article in that language; the navigation, sidebar, table of contents, and body text all switch to the target language together.

## URL Rules

Each language has its own URL prefix; the same article differs across languages only by that prefix:

```text
/canvas/i18n/          → Simplified Chinese (default language, no prefix)
/en/canvas/i18n/       → English
/ja/canvas/i18n/       → Japanese
/zh-tw/canvas/i18n/    → Traditional Chinese
```

- The language is encoded directly in the URL, so a switched page can be bookmarked and shared as-is, and search engines can index each language separately;
- Internal links that appear on a page (navigation, sidebar, recommended links in the body) automatically carry the current language prefix, so readers who keep reading within one language are never bounced back to a Chinese page;
- Every language version is an independent static page generated at build time, and the page's `<html lang>` attribute matches the language, so screen readers and translation tools can identify it correctly.

## What Happens When a Translation Is Missing

When a translation is missing, Starlight can generate the target-language route using the default Simplified Chinese body. This is a technical fallback, not an accepted release policy: the page can still declare the target language while its body is Chinese.

This project requires the homepage and all articles to be maintained across all 10 languages. `node scripts/audit-i18n.mjs` checks missing or extra pages, Frontmatter, headings, and code-fence structure. Missing translations return a non-zero exit code and block `pnpm run verify` and CI. Add or update the corresponding content in every language before publishing; do not publish Chinese first and fill in translations later. A successful `pnpm run build` alone does not mean the release checks passed.

## How It Works

The multilingual capability is carried by the internationalization mechanisms of Astro and Starlight. The build process works as follows:

1. **Content directories are split by language**: documents in the default language live in `src/content/docs/` (Simplified Chinese), and other languages live under `src/content/docs/<language>/` with a directory structure that mirrors the Chinese one exactly. For example, the English edition of "Multilingual Support & Language Switching" is `src/content/docs/en/canvas/i18n.md`;
2. **All language pages are generated at build time**: `astro build` reads the `locales` configuration in `astro.config.mjs` and produces a complete set of static pages for each language;
3. **UI strings are rendered per language**: header navigation, search hints, table-of-contents titles, and other UI text are output in the target language at build time by components calling `getTranslation(key, lang)`; there is no runtime replacement script on the page;
4. **Internal body links are localized automatically**: the `rehypeLocalizeInternalLinks` plugin in the build pipeline automatically adds the current language prefix to `/canvas/xxx` internal links inside translated body text;
5. **Full-text search is isolated per language**: Pagefind builds a separate index for each language, so searching on an English page returns only English results.
6. **Localized body images and checks**: `rehypeLocalizeDiagramImages` rewrites `/images/canvas/<file>` to `/images/canvas/<lang>/<file>` when a matching localized image exists; otherwise it technically keeps the original. However, the release check `check-localized-images.mjs` requires localized images unless they are genuinely shared assets, such as third-party UI screenshots registered in `SHARED_ALLOWLIST`. Image fallback does not waive translation requirements;
7. **Asides and footnotes follow the page language**: `rehypeLocalizeAsides` and `rehypeLocalizeFootnotes` rewrite aside titles and footnote labels from the language directory of the source file — Starlight infers the language from an absolute path during remark, while a local build passes a relative path, so without this every label would fall back to Chinese;
8. **hreflang and the 404 page**: after the build, `hreflangXDefault()` adds one `hreflang="x-default"` link per page pointing at the Simplified Chinese version, and `src/pages/404.astro` reuses the same dictionary to render its message in the browser language, with the language menu linking to each language's home page.

## For Developers: How to Add a Language

Taking Italian (Italiano, code `it`) as an example:

1. **Register the route and directory**: add `it: { label: 'Italiano', lang: 'it' }` to `locales` and `it` to `LOCALE_DIRS` in `astro.config.mjs`, so link, image, redirect, and language-metadata processing recognizes the new directory.
2. **Translate the sidebar, asides, and footnotes**: complete `SIDEBAR_I18N` in the same file; add `it: 'it.json'` to `LOCALE_TRANSLATION_FILES` and Italian entries to `FOOTNOTE_LABELS` and `FOOTNOTE_BACK_LABELS`.
3. **Translate UI strings**: register the code, name, abbreviation, and directory in `SUPPORTED_LANGUAGES` in `src/utils/i18n.ts`, and supply every key in `UI_TRANSLATIONS`, including search, Pagefind, and 404 messages.
4. **Translate all content**: create `src/content/docs/it/index.mdx` and complete translations in `src/content/docs/it/canvas/`, matching the default-language files one for one. Keep Frontmatter keys, heading levels, and code-fence structure aligned; copying Chinese placeholders is not a translation.
5. **Prepare localized images**: put matching filenames under `public/images/canvas/it/`. Only genuinely shared images belong in `SHARED_ALLOWLIST` in `scripts/check-localized-images.mjs`. If using the diagram generator, add `scripts/diagram-i18n/it.mjs` and register it in `LOCALES` in `scripts/generate-diagram-locales.mjs`; if using the screenshot tool, update `LOCALES` and `SEARCH_WORDS` in `scripts/capture-ui-shots.mjs`.
6. **Extend the checks**: add `it` to `locales` and `LATIN` in `scripts/audit-i18n.mjs`, `LOCALES` in `scripts/check-anchors.mjs`, and `LOCALE_DIRS` in `scripts/check-localized-images.mjs`. Add `['it', 'it']` to the language-code/directory map `LANG_DIRS` in `scripts/check-links.mjs`. `scripts/check-images.mjs` scans image directories recursively and needs no separate language registration.
7. **Check sources and images first**: run `node scripts/audit-i18n.mjs` and `node scripts/check-images.mjs` from the repository root. The latter checks only PNG signatures and minimum size, not translated text or visual layout.
8. **Verify before publishing**: run `pnpm run verify`, which builds the site and checks localized image references, links, anchors, and language metadata. Use `pnpm run preview` to inspect the new language's homepage, articles, language switching, and site-wide search. Fix all failures rather than removing checks to publish.

## For Developers: How to Add or Modify UI Strings

When adding a new UI element, add its strings to `UI_TRANSLATIONS` in `src/utils/i18n.ts`:

```typescript
// File path: src/utils/i18n.ts
// The dictionary is organized in two levels, "language → string key", matching the lookup order of getTranslation
export const UI_TRANSLATIONS: Record<string, Record<string, string>> = {
  // Step 1: add the string under the default language zh-CN (if missing, the UI falls back to showing the key name)
  'zh-CN': {
    'nav.plugins': '插件生态',
    // ...other existing strings
  },
  // Step 2: add translations under the same key for other languages; languages without one fall back to Chinese
  en: {
    'nav.plugins': 'Plugins',
  },
  ja: {
    'nav.plugins': 'プラグイン',
  },
};
```

Then call `getTranslation` in the component, passing in the current language:

```astro
---
import { getLangFromLocale, getTranslation, localizedHref } from '../../utils/i18n';
const lang = getLangFromLocale(Astro.currentLocale);
---

<a href={localizedHref('/plugins/', lang)}>{getTranslation('nav.plugins', lang)}</a>
```

Strings are rendered at build time as static text in the target language, with no runtime overhead.

The example shows only three language branches. New strings still need translations in every registered language; Chinese fallback is a safeguard, not completed translation.
