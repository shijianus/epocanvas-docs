Чтобы читатели понимали, какой версии продукта соответствует текущая документация, а команда могла упорядоченно отслеживать историю изменений, **EpoCanvas Docs** использует семантические номера версий и фиксированный процесс выпуска.

---

## 1. Правила семантических номеров версий (SemVer)

Стабильные версии используют `vMAJOR.MINOR.PATCH`, предварительные — дополнительный идентификатор, как текущая кандидатная `v1.3.2-beta.1`. Это не означает публикацию Release или развёртывание в рабочей среде.

| Тип изменения | Пример | Когда срабатывает |
| :--- | :--- | :--- |
| **Основная версия (Major)** | `v2.0.0` | Крупный рефакторинг документационной системы (например, обновление основной версии Astro, полная замена макета). |
| **Минорная версия (Minor)** | `v1.2.0` | Заметные новые функции: новые разделы документации, добавление новых языков, обновление дизайн-системы и т.п. |
| **Патч-версия (Patch)** | `v1.2.1` | Мелкие изменения: исправление опечаток, обновление примеров кода, корректировка мелких стилей. |

## 2. Стандартный процесс выпуска новой версии из 3 шагов

### Шаг 1: описать обновления (`RELEASE_NOTES.md`)

Опишите обновление в `RELEASE_NOTES.md` в корне проекта: этот файл станет текстом GitHub Release. Первая строка должна в точности иметь вид `# EpoCanvas Docs v<версия>` с версией из `package.json`; формат проверяет `verify:config`. Ниже приведён только пример формата: для публикации выберите ещё не использованную версию. В тексте предварительного выпуска также укажите `candidate` или `prerelease`.

```markdown
# EpoCanvas Docs v1.2.1

2026-09-14

### Исправления
- Исправлена опечатка в команде в разделе о развёртывании.
- Скриншоты интерфейса обновлены до последней версии.
```

### Шаг 2: обновить номер версии в package.json

Бейдж версии в панели навигации автоматически связан с полем `version` в `package.json`, которое служит единственным источником данных о версии для всего сайта (Single Source of Truth). Обновите номер версии в `package.json` (или выполните `pnpm version patch --no-git-tag-version`) — бейдж в верхней панели автоматически синхронизируется с новым номером, вручную менять его в нескольких местах не нужно:

```json
{
  "name": "epocanvas-docs",
  "version": "1.2.1"
}
```

### Шаг 3: зафиксировать код и поставить Git-тег

```bash
# 1. Зафиксировать все изменения
git add .
git commit -m "chore(release): bump version to v1.2.1"
git push origin main

# 2. Поставить соответствующий тег версии и отправить его
git tag v1.2.1
git push origin v1.2.1
```

## 3. Автоматический конвейер публикации на GitHub Actions

Актуальное определение находится в [`.github/workflows/release.yml`](https://github.com/shijianus/epocanvas-docs/blob/main/.github/workflows/release.yml); полный YAML здесь не дублируется. Процесс запускается при отправке тега `v*`. Перед созданием тега выполните локальную проверку ниже: она не записывает Releases в GitHub и не развёртывает сайт.

```bash
pnpm run verify
```

1. Задание `validate` работает только с правами чтения `contents: read` и сначала выполняет полную проверку `pnpm run verify`.
2. Только после успешной проверки задание `publish` получает права `contents: write` для создания или обновления GitHub Release с описанием из `RELEASE_NOTES.md`.
3. Существующий Release обновляется на месте, без удаления и повторного создания. GitHub определяет `Latest` среди стабильных выпусков по версии; предварительные выпуски не помечаются как `Latest`. История доступна через бейдж версии в шапке.

:::note
Этот процесс только создаёт или обновляет GitHub Releases и не развёртывает сайт автоматически. Слияние в `main` также не запускает развёртывание. Для публикации используется локальная команда `pnpm run deploy` или отдельно настроенная Git-интеграция хостинга; см. [Развёртывание на Cloudflare Pages](/canvas/cloudflare/).
:::

## 4. Процесс совместной работы над контентом

Когда документацию ведут несколько человек, работа строится по фиксированной схеме «ветка → проверка → слияние → публикация», чтобы содержимое сайта всегда собиралось:

```text
Ветка main (источник выпусков; сайт обновляется только после развёртывания)
  │
  ├─ 1. От ветки main создаётся функциональная ветка   git checkout -b docs/new-guide
  ├─ 2. Написание/правка Markdown
  ├─ 3. Локальная самопроверка                          pnpm run verify
  ├─ 4. Отправка ветки и открытие Pull Request          запускает полную проверку CI
  ├─ 5. После одобрения слияние в main                  не развёртывает сайт автоматически
  └─ 6. При необходимости выпустить версию ставится тег v*   запускает конвейер GitHub Release
```

### На что обращать внимание при проверке Pull Request

CI (`build.yml`) запускает `pnpm run verify`: тесты, проверки конфигурации и типов Astro, сборку и проверки содержимого и артефактов. Внешний вид страниц по-прежнему проверяется вручную:

- **Работоспособность ссылок**: ведут ли куда-то новые внутренние ссылки и якоря; зарегистрировано ли перенаправление для документов со сменившимся путём;
- **Результат рендеринга**: корректно ли отображаются на странице синтаксис `:::` в выносках и аннотации блоков кода (CI визуальную часть не проверяет);
- **Соответствие текста и изображений**: снабжены ли новые скриншоты подписями и достаточно ли они чёткие;
- **Правила именования**: имена файлов в нижнем регистре с дефисами, заполненные `title` и `description` во Frontmatter.

### Рекомендации по распределению ролей

| Роль | Обязанности |
| :--- | :--- |
| Автор документации | Пишет контент, проверяет локально, инициирует PR |
| Проверяющий | Сверяет результат рендеринга и ссылки, сливает код |
| Администратор выпуска | Ставит теги версий, ведёт `RELEASE_NOTES.md`, синхронизирует бейдж версии в панели навигации |

## 5. Проверка сборки в CI

`.github/workflows/build.yml` выполняет полную проверку при отправке изменений в `main` и в Pull Requests. CI использует Node.js 22.23.4 из `.node-version` и pnpm 10.34.5. Перед коммитом выполните ту же самопроверку локально:

```bash
pnpm run verify
```
