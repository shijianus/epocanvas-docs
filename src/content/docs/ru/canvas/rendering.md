На этой странице подробно описаны правила рендеринга **EpoCanvas Docs**: через какие этапы обработки проходит Markdown-файл, во что превращается каждый синтаксис и какой синтаксис не поддерживается. Прочтите её один раз перед написанием документации — это позволит избежать большинства проблем с вёрсткой.

---

## Конвейер рендеринга: от .md-файла до страницы на сайте

![Схема конвейера рендеринга Markdown в EpoCanvas Docs: полный процесс из 5 шагов — от сканирования исходников Markdown, разбора AST по GFM и подсветки кода до сборки макета из 7 кастомных компонентов, генерации статического HTML и индекса Pagefind](/images/canvas/docs-render-pipeline.svg)

*Рисунок: 5 шагов конвейера рендеринга Markdown. Шаги выполняются по порядку на этапе сборки; результат сборки — чисто статические файлы, без накладных расходов клиентского фреймворка во время выполнения.*

От сохранения до появления перед читателем Markdown-файл проходит следующие пять этапов:

1. **Сбор контента**: при запуске или сборке Astro сканирует каталог `src/content/docs/`, регистрирует каждый файл `.md` / `.mdx` как запись контента и проверяет Frontmatter (отсутствие `title` сразу вызывает ошибку).
2. **Компиляция Markdown**: основной текст компилятором Markdown (с расширениями GFM) преобразуется в HTML. Расширенный синтаксис — таблицы, списки задач, зачёркивание и т.д. — срабатывает на этом шаге.
3. **Подсветка блоков кода**: все кодовые ограждения обрабатывает Expressive Code, создавая блоки кода с подсветкой синтаксиса, панелью заголовка, номерами строк и кнопкой копирования.
4. **Применение макета сайта**: скомпилированный HTML вставляется в каркас страницы Starlight — верхняя панель, левое оглавление и правое оглавление страницы рендерятся кастомными компонентами из `src/components/starlight/`.
5. **Генерация индекса и статических файлов**: при `pnpm run build` Pagefind обходит все итоговые страницы и извлекает полнотекстовый индекс; чистый HTML в каталоге `dist/` можно размещать на любом статическом сервере.

:::note
Весь описанный процесс выполняется один раз на этапе сборки. После публикации сайта сервер не участвует: все взаимодействия (поиск, переключение темы, переключение языка) происходят в браузере.
:::

## Правила Frontmatter

- `title` **обязателен**; при его отсутствии сборка завершается ошибкой `InvalidInputError`;
- `description` рекомендуется заполнять: он показывается в результатах поисковых систем и в карточках при обмене ссылками;
- Frontmatter должен быть корректным YAML-блоком в самом начале файла; все три дефиса в разделителях обязательны.

## Правила заголовков

| Правило | Пояснение |
| :--- | :--- |
| Не пишите заголовок первого уровня `#` в основном тексте | `title` из Frontmatter уже отрендерен как крупный заголовок страницы; ещё один `#` в тексте даст два крупных заголовка |
| Основной текст начинается с заголовка второго уровня `##` | `##` и `###` автоматически попадают в правое «оглавление страницы» |
| `####` и глубже не попадают в оглавление | Более глубокие уровни рендерятся только как стили основного текста |
| Текст заголовка превращается в якорь | Якорь китайского заголовка — сами китайские символы, например `#标题规则` |

## Правила выносок (Asides)

Выноски используют синтаксис тройного двоеточия Starlight и поддерживают 4 типа:

```markdown
:::note
Дополнительное пояснение.
:::

:::tip
Небольшой приём для повышения эффективности.
:::

:::caution
Риск, на который стоит обратить внимание, или операция, в которой легко ошибиться.
:::

:::danger
Предупреждение о высокой опасности: потеря данных или необратимые операции.
:::
```

После типа можно добавить собственный заголовок: `:::tip[安装提速]`.

:::caution
Обратите внимание на две частые ошибки:

- синтаксис цитаты в стиле GitHub `> [!TIP]` **не поддерживается**: написанный `[!TIP]` отобразится обычным текстом внутри цитаты;
- `:::important` и `:::warning` **не являются допустимыми типами**: ошибки не будет, но они молча отрендерятся как обычные абзацы.

При переносе старых документов: `> [!NOTE]` → `:::note`, `> [!WARNING]` → `:::caution`, `> [!CAUTION]` → `:::danger`.
:::

## Правила блоков кода

Кодовые ограждения (три обратных апострофа) рендерит Expressive Code; поддерживаются следующие аннотации (пишутся после обратных апострофов первой строки):

| Аннотация | Назначение | Пример |
| :--- | :--- | :--- |
| Идентификатор языка | Определяет схему подсветки синтаксиса | <code>```ts</code> |
| `title="..."` | Показывает панель заголовка с именем файла | <code>```ts title="src/config/site.ts"</code> |
| `{2}` / `{2-4}` | Подсвечивает указанные строки | <code>```ts {2}</code> |
| `lang="diff"` или `diff` | Показывает добавленные и удалённые строки в красно-зелёном сравнении | <code>```diff</code> |
| `bash` / `sh` и другие терминальные языки | Рендерится с рамкой в стиле терминала | <code>```bash</code> |

К каждому блоку кода автоматически добавляется кнопка копирования одним нажатием; текст кода попадает в поисковый индекс Pagefind, поэтому ключевые слова из кода можно находить поиском напрямую.

## Правила изображений

- Изображения хранятся в едином каталоге `public/images/canvas/` и подключаются абсолютным путём: `![说明](/images/canvas/xxx.png)`;
- архитектурные и процессные схемы — в векторном формате `.svg`, скриншоты интерфейса — в сжатом `.png`;
- описание обязательно к заполнению: это альтернативный текст на случай неудачной загрузки изображения и основа для доступности;
- **в текущей версии рендеринг диаграмм Mermaid не встроен**: ограждение ` ```mermaid ` отобразится как обычный блок кода с исходным кодом. Если нужна блок-схема, сначала экспортируйте SVG в mermaid.live или подобном инструменте, а затем вставьте её как изображение.

## Правила ссылок

- **Внутренние ссылки**: указывайте полный путь, начинающийся и заканчивающийся на `/`, например `/canvas/deployment/`. После изменения пути документа старый путь нужно зарегистрировать в таблице `redirects` в `astro.config.mjs`;
- **Якорные ссылки**: `/canvas/rendering/#代码块规则` ведёт сразу к нужному разделу этой страницы;
- **Внешние ссылки**: достаточно указать полный URL; в основном тексте они отображаются цветом темы.

## Прочее поведение рендеринга

| Синтаксис | Результат рендеринга |
| :--- | :--- |
| `**加粗**`, `*斜体*`, `~~删除线~~` | Соответствующее начертание текста |
| `行内代码` | Капсула моноширинным шрифтом цвета темы |
| Запись <kbd>Ctrl</kbd>+<kbd>K</kbd> | Обозначение клавиш в стиле клавиатурных клавиш |
| Таблицы GFM | Таблицы данных с рамкой и подсветкой при наведении |
| Список задач `- [x]` | Визуальные чекбоксы (в отключённом состоянии) |
| Сноски `[^名称]` | Верхний индекс в основном тексте + список сносок внизу страницы, с переходами по клику в обе стороны |
| Цитата Markdown `>` | Вертикальная линия цвета темы слева + светлый фон |
| Разделитель `---` | Тонкая линия через всю область основного текста |

:::tip
Если не уверены, как отрендерится тот или иной синтаксис, самый надёжный способ: запустите `pnpm run dev`, вставьте небольшой фрагмент в тестовый документ и убедитесь в браузере своими глазами, прежде чем использовать его в основном документе.
:::
